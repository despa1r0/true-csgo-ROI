# Roadmap trueROI

Этот документ — последовательный план развития trueROI. Приоритет у функций,
которые помогают принять более реалистичное торговое решение, а не только
увидеть максимальный процент ROI.

## Принципы

- Деньги считаются на backend в центах; интерфейс не является источником
  формул и комиссий.
- Условия площадок, особенно комиссии и KYC/вывод, должны иметь дату проверки
  и ссылку на первоисточник: они могут меняться.
- Показатели `ROI`, ликвидности и уверенности в данных не следует смешивать.
  ROI остаётся точным финансовым расчётом, а smart-оценка объясняет риск и
  скорость выхода из сделки.
- Данные, которых API площадки не даёт, не надо подменять догадкой. В UI нужно
  показывать «недостаточно данных» и снижать confidence.

## Этап 0. Базовая надёжность

### Цели

1. Исправить шаблон окружения `.env.example`:
   `DATABASE_URL` сейчас использует `POSTGRESS_PASSWORD` вместо
   `POSTGRES_PASSWORD`, а части URL расположены неверно. Формат должен быть
   `postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}`.
2. Добавить миграции PostgreSQL через Alembic. Сейчас схема изменяется
   Python-кодом при запуске, что удобно локально, но опасно для обновлений
   production-БД.
3. Зафиксировать единые команды для разработчика: `test`, `lint`, `build`,
   `up`, `down`, `logs`, `migrate` (Makefile и/или PowerShell-скрипт).
4. Удалить или явно пометить legacy-папку `frontend`, если production использует
   только `frontend-react`, чтобы два интерфейса не расходились.

### Критерий готовности

Новый разработчик копирует `.env.example`, выполняет одну documented-команду и
получает работающее приложение; обновление схемы выполняется отдельной,
повторяемой миграцией.

## Этап 1. Страница «Площадки»

### Что сделать

Добавить маршрут `/marketplaces`, пункт навигации и страницу со списком
площадок. `GET /api/marketplaces` уже возвращает комиссии, методы и
capabilities, поэтому первую версию можно построить без нового внешнего API.

Карточка и детальная страница площадки должны показывать:

| Блок | Содержание |
|---|---|
| Статус интеграции | Есть live-данные, только калькулятор, нет API, временно недоступна. |
| Торговля | Можно ли купить, выставить лот, получить buy orders, quick sell, историю продаж. |
| Комиссии | Пополнение, продажа и вывод по каждому методу; процент и фиксированная часть. |
| Условия | Валюта, поддерживаемые методы, KYC, лимиты, минимальный вывод, trade lock, ориентировочный срок выплаты. |
| Достоверность | Дата проверки, версия конфигурации, ссылка на правила/API площадки и дисклеймер о региональных условиях. |

### Модель данных

На первом шаге дополнить существующий `MarketplaceConfig`: `website_url`,
`terms_url`, `api_docs_url`, `kyc_required`, `trade_lock_description`,
`minimum_withdrawal`, `withdrawal_time_description`, `last_verified_at`.
Для полей, сильно зависящих от страны или способа оплаты, хранить описание и
ссылку, а не выдавать одно значение за универсальную истину.

Позже, когда потребуется редактирование без релиза, вынести справочную часть
в таблицу `marketplace_profiles` и небольшую admin-панель. Правила расчёта
комиссий пока оставить version-controlled в backend, чтобы изменения проходили
code review и тесты.

### Критерий готовности

Пользователь за одну страницу понимает, на каких площадках можно совершить
реальную сделку, какие комиссии попадут в расчёт и насколько свежа информация.

## Этап 2. Собственная история рынка и фоновые задачи

### Что сделать

1. Добавить таблицы снимков цены и агрегатов продаж: например,
   `market_price_snapshots` и `market_sales_snapshots`.
2. Запускать worker по расписанию: обновлять популярные предметы чаще,
   редкие — реже; уважать rate limits каждого провайдера.
3. Хранить timestamp, источник, валюту, цену, объём/число продаж, best bid/ask
   и признак ошибки получения данных.
4. Добавить retention policy: сырые частые снимки хранить ограниченный срок,
   затем сохранять часовые/дневные агрегаты.

### Redis: когда и зачем добавлять

Redis не нужен как замена PostgreSQL: PostgreSQL остаётся источником истины
для каталога, сделок и истории. Redis следует внедрять вместе с worker, когда
появится хотя бы одна из задач ниже:

- очередь фоновых задач (например, Dramatiq, RQ или ARQ);
- общий для нескольких API-реплик rate limit внешних API;
- distributed lock `refresh:<marketplace>:<variant_id>`, чтобы несколько
  запросов не обновляли один предмет параллельно;
- короткий cache горячих ответов и защита от cache stampede.

Практичный порядок: сначала реализовать один worker и запись snapshots в
PostgreSQL, затем добавить Redis как broker/lock/rate-limit. Метрики cache hit,
длины очереди и ошибок задач обязательны до масштабирования.

### Критерий готовности

Через 2–4 недели накопления данных графики и оценка ликвидности строятся из
собственной истории, а не только из того, что площадка отдаёт в момент запроса.

## Этап 3. Новая модель ликвидности и smart-оценка сделки

### Проблема

Высокий ROI сам по себе не означает хорошую сделку. Предмет может продаваться
неделями, иметь слишком широкий spread или не иметь достаточного спроса. При
этом изменять формулу реальной прибыли нельзя: она остаётся прозрачной.

```text
effective_buy = buy_price + buy_fees
effective_payout = sell_price - sell_fees
profit = effective_payout - effective_buy
roi = profit / effective_buy * 100
```

### Разделить три показателя

| Показатель | Вопрос | Пример данных |
|---|---|---|
| ROI и profit | Сколько денег получится при продаже по выбранной цене? | Цена покупки/продажи и комиссии. |
| Liquidity score, 0–100 | Насколько быстро и реалистично можно выйти из позиции? | Продажи за период, спрос, spread, глубина стакана. |
| Data confidence, 0–100 | Насколько можно доверять этой оценке? | Свежесть, полнота и размер выборки данных. |

### Первая объяснимая формула liquidity score

Для старта не нужен ML. Использовать нормализованные компоненты в диапазоне
0–100 и показывать их пользователю:

```text
liquidity_score =
  0.40 * sales_velocity_score +
  0.25 * spread_score +
  0.20 * order_book_depth_score +
  0.15 * price_stability_score
```

- `sales_velocity_score`: число подтверждённых продаж за 7/14/30 дней с
  поправкой на период наблюдения;
- `spread_score`: меньше разница между лучшим ask и best bid — выше оценка;
- `order_book_depth_score`: объём заявок на покупку около целевой цены;
- `price_stability_score`: штраф за резкие колебания цены и слишком малую
  выборку.

Если нет sales history или buy orders, компонент не выдумывается. Вес доступных
компонентов нормализуется, а `data_confidence` понижается. Страница должна
объяснить: «ликвидность 42/100: мало продаж и spread 18%; данных за 7 дней».

### Smart deal score и рекомендация

Отдельно вычислять `smart_deal_score`, не называя его ROI:

```text
profit_score = min(100, roi / target_roi * 100)
smart_deal_score =
  0.45 * profit_score +
  0.40 * liquidity_score +
  0.15 * data_confidence
```

`target_roi` должен быть настройкой пользователя, например 15%. Также ввести
жёсткие стоп-правила: не рекомендовать сделку при отрицательной прибыли, при
неизвестной цене быстрой продажи, при слишком низком confidence или когда
ликвидность ниже минимального порога пользователя.

Результат в интерфейсе — не просто число, а объяснимое предложение:

- **Сильная сделка** — прибыль и ликвидность выше порогов;
- **Можно рассмотреть** — хорошая прибыль, но средняя скорость выхода;
- **Осторожно** — высокий ROI компенсируется слабой ликвидностью;
- **Не рекомендовать** — не проходит стоп-правила.

Показывать ожидаемый сценарий выхода: продажа по лучшему ask, продажа в buy
order/quick sell, оценочное число дней до продажи и причины штрафов. Сначала
проверить веса на сохранённых снимках и ручных сделках, затем калибровать их,
а не объявлять формулу окончательной.

### Критерий готовности

Карточка сделки показывает ROI, liquidity score, confidence, smart deal score
и 2–4 понятные причины оценки. Сделка с ROI 80% и ликвидностью 10/100 не
попадает в лучшие рекомендации без явного предупреждения.

## Этап 4. Инструменты трейдера

1. Сканер возможностей между площадками: фильтры по profit, ROI, liquidity,
   confidence, цене и конкретной площадке.
2. Watchlist: отслеживание предмета, float, sticker/charm и целевой цены.
3. Уведомления: цена ниже порога, сделка стала прибыльной, появился нужный лот.
4. Журнал сделок: ручные покупка/продажа, факт комиссий, фактическая прибыль и
   сравнение прогноза с результатом.
5. Поиск конкретных stickers/charms по нормализованному имени или ID.

## Этап 5. Подключение новых площадок

Для каждой площадки использовать одинаковый checklist:

1. Проверить ToS, официальный API, rate limits, требования ключа и право
   хранить/показывать данные.
2. Добавить профиль и capabilities в реестр, но не выставлять `supports_*` в
   `true` до реально работающего адаптера.
3. Написать изолированный adapter и нормализовать ответы в существующие модели.
4. Добавить fixtures и контрактные тесты: пустой ответ, rate limit, timeout,
   изменённый ответ API, частично доступные данные.
5. Добавить источник комиссий, дату проверки и экранный статус доступности.
6. Включить площадку в production сначала в режиме наблюдения: метрики ошибок,
   ограниченный трафик, затем полный rollout.

## DevOps-практика: учебный трек для junior DevOps

Ниже не список технологий «для галочки», а порядок, в котором каждая новая
технология решает конкретную проблему проекта.

### 1. Linux, сеть и Docker Compose

**Зачем:** понимать, из каких контейнеров состоит приложение и почему API не
видит БД.

Изучить:

- процессы, порты, DNS, переменные окружения, права файлов и логи в Linux;
- image, container, volume, network, layer и multi-stage build в Docker;
- `docker compose`, healthcheck, `depends_on`, named volumes и restart policy.

Практика в проекте:

1. Нарисовать архитектуру: browser → FastAPI → PostgreSQL и отдельно внешние
   marketplace API.
2. Научиться диагностировать `docker compose ps`, `logs`, `exec`, healthcheck
   PostgreSQL и `/api/health`.
3. Добавить `.dockerignore`, запуск контейнера от non-root пользователя и
   минимально необходимые пакеты в образ.
4. Документировать в README типовые поломки: занятый порт, не стартовал Docker,
   не прошёл seed, неверный `DATABASE_URL`.

Готово, когда можно с нуля запустить стек, намеренно сломать переменную БД и
самостоятельно найти причину по логам и healthcheck.

### 2. Качество кода и CI в GitHub Actions

**Зачем:** pull request не должен ломать main.

Текущий CI уже запускает backend/frontend тесты и Docker build. Развить его
постепенно:

1. Backend: добавить `ruff check`, `ruff format --check`, затем `mypy` или
   `pyright` после настройки типов.
2. Frontend: добавить `npm run lint` (ESLint), typecheck и покрытие Vitest.
3. Собирать coverage-отчёт, но не ставить высокий порог сразу; увеличивать его
   только для нового кода.
4. Добавить integration smoke test: поднять Compose с тестовой БД, дождаться
   healthcheck и вызвать `/api/health`, `/api/marketplaces`.
5. Добавить branch protection: merge в `main` только при зелёных required
   checks и хотя бы одном review.

Готово, когда плохая миграция, ошибка TypeScript или неработающий Dockerfile
останавливают merge автоматически.

### 3. Конфигурация, секреты и supply-chain security

**Зачем:** ключи маркетплейсов нельзя положить в git или Docker image.

Практика:

1. Хранить `.env` только локально, а в GitHub — Secrets/Environment secrets.
2. Добавить secret scanning (например, Gitleaks) в CI и включить GitHub secret
   scanning, если он доступен в репозитории.
3. Проверять образы и зависимости Trivy; настроить Dependabot для Python,
   npm и GitHub Actions.
4. Пиновать GitHub Actions по commit SHA либо регулярно обновлять их через
   Dependabot. Использовать минимальные `permissions` для workflow.
5. Генерировать SBOM — список библиотек внутри release-образа; он полезен при
   разборе уязвимостей.

Готово, когда CI обнаруживает случайно добавленный тестовый ключ и известную
критическую уязвимость в образе.

### 4. Delivery: образ, registry и deployment

**Зачем:** релиз должен быть повторяемым, а откат — быстрым.

Практика:

1. После успешного merge/tag собирать образ и публиковать его в GHCR.
2. Тегировать образ как `vX.Y.Z` и commit SHA; production никогда не должен
   использовать плавающий тег `latest`.
3. Добавить release workflow: build → test → scan → push → deploy.
4. Для первого production использовать VPS и Docker Compose: Nginx или Caddy
   как reverse proxy, HTTPS через Let's Encrypt, закрытые наружу PostgreSQL и
   Redis.
5. Подготовить rollback: заменить `IMAGE_TAG` на предыдущий проверенный тег,
   выполнить `docker compose up -d`, проверить health endpoint.

Готово, когда можно задеплоить tagged image и откатить предыдущую версию без
ручной пересборки на сервере.

### 5. База данных и резервные копии

**Зачем:** volume Docker не является резервной копией.

Практика:

1. Освоить `pg_dump`, `pg_restore`, роли PostgreSQL и миграции Alembic.
2. Делать ежедневный backup PostgreSQL в отдельное хранилище, зашифрованный и
   с retention policy.
3. Регулярно выполнить restore в отдельную тестовую БД и записывать результат.
4. Перед миграцией production создавать backup и иметь инструкцию rollback.

Готово, когда база восстанавливается из backup на чистом окружении, а это
проверено не только «на словах».

### 6. Наблюдаемость: логи, метрики, алерты

**Зачем:** после deployment надо видеть проблему до жалобы пользователя.

Практика:

1. Перевести backend на структурированные JSON-логи: request ID, endpoint,
   HTTP status, duration, marketplace, cache status — без API-ключей и
   персональных данных.
2. Разделить `liveness` («процесс жив») и `readiness` («может обслуживать
   трафик, БД доступна»).
3. Экспортировать Prometheus-метрики: latency/ошибки API, ошибки и время
   запросов к каждой площадке, cache hit ratio, свежесть данных, worker jobs,
   размер очереди Redis.
4. Поднять локально Prometheus + Grafana в Compose и собрать один dashboard.
5. Добавить Sentry для ошибок приложения и минимум два alert: API недоступен,
   процент ошибок адаптера резко вырос.

Готово, когда можно отключить один адаптер и по графику/алерту увидеть, что
сломалось, на какой площадке и с какого времени.

### 7. Redis и фоновые workers

**Зачем:** обрабатывать периодический сбор цен надёжно, не задерживая HTTP
запрос пользователя.

Практика:

1. Добавить Redis service в Compose с password, volume и healthcheck.
2. Выбрать одну библиотеку очереди: для Python-проекта хороши Dramatiq, RQ или
   ARQ. Не внедрять несколько одновременно.
3. Вынести в задачу обновление одной площадки/предмета, добавить retry с
   exponential backoff и idempotency key.
4. Добавить scheduled job и dashboard/метрики очереди.
5. Проверить сценарии: Redis перезапущен, задача упала, API площадки вернул
   429, две одинаковые задачи пришли одновременно.

Готово, когда worker переживает перезапуск, не дублирует snapshots и не
нарушает rate limit API.

### 8. Инфраструктура как код — после освоения Compose

Начинать Terraform, Ansible и Kubernetes стоит не одновременно и не раньше,
чем станет понятен ручной deployment.

Рекомендуемый путь:

1. **Ansible**: описать подготовку VPS, Docker, firewall, deploy directory и
   обновление Compose. Это лучший первый IaC-инструмент для данного проекта.
2. **Terraform**: создать VPS, сеть, firewall/DNS у выбранного cloud-провайдера.
3. **Kubernetes**: только если действительно потребуются несколько сервисов,
   autoscaling и несколько реплик. Для одной VPS Compose проще и надёжнее.

### Пример порядка обучения

1. Docker/Compose и Linux.
2. Git/GitHub Actions, lint и тесты.
3. Docker registry, tagged releases, VPS deployment и HTTPS.
4. PostgreSQL backups и миграции.
5. Логи, Prometheus/Grafana, Sentry.
6. Redis + worker.
7. Ansible, затем Terraform при необходимости.
