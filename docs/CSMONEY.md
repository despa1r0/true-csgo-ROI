# CS.MONEY

## Поиск предмета вне каталога

Обычный `/api/items/search` работает только с локальной БД. Если он не находит
совпадений и фильтры каталога не выбраны, интерфейс предлагает отдельную кнопку
«Искать на CS.MONEY». Набор текста и повторные клики сами по себе запросов к
площадке не создают. `POST /api/market/csmoney/search` принимает JSON
`{"query":"..."}`, повторно проверяет локальный каталог и возвращает `202` с
`request_id` и `status`. Запрос длиной 2–100 печатных символов нормализуется;
одинаковые запросы (без учёта регистра и лишних пробелов) совместно используют
одну активную задачу. `GET /api/market/csmoney/search/{request_id}` выдаёт
`queued`, `running`, `complete`, `empty`, `blocked`, `error` или `expired`, время,
ошибку и JSON результата.

Отдельная таблица `csmoney_text_search_jobs` не ссылается на `variant_id`.
Воркер обрабатывает её перед `csmoney_refresh_jobs`: открывает новую вкладку
через `page.context.new_page()` в текущей браузерной сессии, закрывает её после
снимка и использует тот же интервал между обращениями к витрине. Никакого
Playwright из API и второго браузера нет. Синхронный воркер выполняет задачи
последовательно. При 403, 429 или Cloudflare challenge поиск получает `blocked`,
а общий circuit breaker приостанавливает обращения к витрине на время
`CSMONEY_STOREFRONT_RETRY_SECONDS`. Обход защиты не выполняется.

Результат хранится 30 минут после завершения; незавершённая задача истекает
через 30 минут после создания. По истечении срока JSON удаляется при следующей
операции с очередью, старый `request_id` показывает `expired` ещё до суток,
а новый запрос создаёт новую задачу. Выдаются максимум 20 лотов
первой отсортированной страницы: фактическое название, ID лота, цена в USD
центах, ссылка на поиск и доступные float, seed, фаза и изображение. На полной
странице результат помечается `is_partial`: следующие страницы не проверены.
Ссылка ведёт на поиск по площадке, поскольку прямая ссылка по ID лота не
подтверждена. Ни `skins`, ни `skin_variants`, ни таблицы обычных котировок не
пополняются: для расчёта ROI нужен проверенный canonical ID и вариант.

> **Состояние production на 21 сентября 2026 года:** запросы с VPS к storefront
> получают HTTP 403, поэтому конкретные лоты недоступны. Резервный Wiki GraphQL
> также может блокироваться Cloudflare; его успешная работа с VPS пока не
> подтверждена. Подробнее: [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md).

## Источник и валюта

Проверено 20 сентября 2026 года через Camoufox без авторизации. Страница
`/pl/market/buy/?search=<market_hash_name>&order=asc&sort=price` возвращает HTML
со встроенным `inventory.items`: до 60 отсортированных лотов. Коллектор берёт
до 10 разных ID с точным названием варианта и соответствующей фазой. Цена
`pricing.computed` хранится как целое число центов USD. Проверка на сайте:
лот `87677500` имел `pricing.computed=26.01` и отображался как `$26.01` после
выбора USD (в польском интерфейсе — `99.06 zł`).

`/2.0/market/sell-orders` отвечает `403` с кодом `4030`. Параметры `page=2`
и `offset=60` на HTML-странице возвращают ту же первую страницу; курсора в
`inventory` нет. Если на полной странице меньше 10 точных лотов, снимок
помечается `is_partial`. Это означает, что следующие лоты не проверены.
При `403` браузерная сессия закрывается. Следующая попытка обращения к витрине
происходит через 6 часов (настраивается `CSMONEY_STOREFRONT_RETRY_SECONDS`).
Пока витрина недоступна, коллектор запрашивает отдельную публичную сводку Wiki Market.
Этот запрос не гарантирован: GraphQL может также вернуть Cloudflare HTTP 403.
Обход проверки безопасности не выполняется.

## Сбор и выдача

Если витрина возвращает 403, воркер пытается вызвать публичный
`get_min_available(name)` на `https://wiki.cs.money/api/graphql`. При успешном
ответе он даёт минимальную цену P2P Market и число предложений для **точного**
`market_hash_name`. Цена сохраняется в USD центах как `wiki_market_summary` и
участвует в сравнении, пока свежая. Это частичная
сводка: ID, float, наклейки и список десяти лотов отсутствуют. Интерфейс
показывает источник и предлагает проверить цену на площадке. Старые отдельные
лоты удаляются при записи сводки, чтобы их не принять за текущие. Эта сводка
не является историей продаж или ценой Trade.

Строка `scheduled N candidate jobs` подтверждает только постановку задач в
очередь. Она не подтверждает успешное получение N вариантов. При работающем
fallback интерфейс всё равно показывает ноль конкретных лотов, поскольку Wiki
не возвращает их ID и свойства.

- Отдельный сервис `csmoney-worker` держит один браузер и делает запросы к
  страницам с интервалом не менее 10 секунд. Обычный TTL кэша — 30 минут.
- Очередь в PostgreSQL дедуплицирует запросы по `variant_id`. Запрос
  пользователя ставит отсутствующий или устаревший вариант с высоким
  приоритетом, а API немедленно возвращает кэш и `refresh_queued`.
- Каждые пять минут планировщик ставит до 30 задач: сначала до 10 вариантов
  с наибольшим наблюдаемым числом продаж за семь дней, затем давно не
  проверявшиеся варианты каталога (минимум сутки). Свободные места от
  востребованных вариантов достаются редким предметам.
- Спрос определяется по свежей истории CSFloat. При её отсутствии берётся
  свежая история CSGO Market. Отдельный сервис `csmoney-demand` постепенно
  запрашивает историю CSGO Market: до пяти запросов за цикл, повторная
  проверка варианта не чаще раза в сутки. История содержит только доступную
  выборку, поэтому число продаж — нижняя оценка, а отсутствие наблюдений
  не считается нулевым спросом.
- Лоты лежат в `marketplace_active_listings`; минимальная цена варианта — в
  `marketplace_listings`. Состояние полноты и времени проверки находится в
  `csmoney_variant_state`, очередь — в `csmoney_refresh_jobs`, сигнал спроса —
  в `csmoney_demand_signals`. Устаревшие цены исключаются из сравнения и ROI.

API: `/api/skins/{skin_id}/market/csmoney`,
`/api/skins/{skin_id}/market/csmoney/listings`,
`/api/variants/{variant_id}/market/csmoney`. Фронтенд показывает время
снимка, неполноту и статус обновления. История продаж и быстрая продажа на
CS.MONEY пока не предоставляются. Ссылка лота ведёт на отсортированный поиск
варианта, поскольку надёжная прямая ссылка на конкретный ID не подтверждена.

## Восстановление браузера и память

Закрытие или падение страницы, контекста либо браузера — отдельная ошибка
инфраструктуры. Воркер закрывает старую сессию и запускает новый Camoufox.
Перед получением следующей задачи проверяются `page.is_closed()` и
`browser.is_connected()`. Если сессия уже закрыта, задачи не забираются из очереди.
Ошибки во время перехода, чтения встроенного JSON и создания вкладки также
передаются в обработчик восстановления.

Неудачная задача каталога повторяется после короткой паузы: сохраняет приоритет,
а эта попытка вычитается из счётчика ошибок провайдера. Текстовый поиск остаётся
`running` до повторного получения lease; исходный срок его жизни не продлевается.
Данные не помечаются свежими при сбое браузера. Восстановление браузера не
включает шестичасовую паузу storefront; 403, 429 и challenge по-прежнему
закрывают общий circuit breaker и переключают сбор каталога на Wiki.

Долгоживущая сессия также обновляется между задачами по возрасту, числу задач
или потреблению памяти. Измеряется память всего контейнера, включая дочерние
процессы Firefox, через cgroup v2 с резервным чтением cgroup v1. Если эти
метрики недоступны (например, при запуске Python на Windows), остаются ротация
по возрасту и числу задач. В Compose задан жёсткий лимит RAM; swap для воркера
отключён. `init: true` обеспечивает сбор завершившихся дочерних процессов.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `CSMONEY_BROWSER_MAX_SESSION_SECONDS` | `1800` | Перезапуск браузера через 30 минут |
| `CSMONEY_BROWSER_MAX_SESSION_JOBS` | `100` | Перезапуск после 100 обработанных задач, включая поиск |
| `CSMONEY_BROWSER_MEMORY_LIMIT_MB` | `1536` | Мягкий порог памяти контейнера в МиБ |
| `CSMONEY_BROWSER_RESTART_DELAY_SECONDS` | `10` | Пауза при восстановлении и отсрочка сбойного lease |
| `CSMONEY_BROWSER_MAX_RESTARTS` | `3` | Предел повторных восстановлений без обработанной задачи |
| `CSMONEY_WORKER_MEMORY_LIMIT` | `2g` | Жёсткий лимит памяти контейнера |

Мягкий порог должен быть ниже жёсткого лимита. Проверка памяти выполняется
между задачами, поэтому во время одного перехода страница может достигнуть
жёсткого лимита раньше. При трёх неудачных восстановлениях без прогресса
воркер завершает процесс с ошибкой: `restart: unless-stopped` в Compose
перезапускает контейнер и освобождает оставшиеся браузерные процессы.
Ошибка запуска/завершения самого Camoufox также приводит к выходу процесса.

В INFO-логах раз в интервал планирования видны `browser session jobs=...`,
`age_seconds` и `memory_mb`. Ротация выводит `reason=age`, `job_limit` или
`memory`; восстановление после сбоя — `reason=browser_unavailable`.
Для проверки на VPS:

```sh
docker compose -f /opt/true-roi/docker-compose.prod.yml logs --tail=100 csmoney-worker
docker stats --no-stream true-roi-csmoney-crawler
```

После восстановления накопленная очередь обрабатывается постепенно с прежним
лимитом запросов. HTTP 200 от API не означает свежесть данных CS.MONEY:
проверяйте время снимка, `source_state` и `refresh_queued`.

Семантика проверки соединения и закрытия сессий описана в
[Playwright Browser API](https://playwright.dev/python/docs/api/class-browser),
ограничения памяти — в
[Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/).

## Отдельная история цен Trade из Wiki

Публичный `POST https://wiki.cs.money/api/graphql` позволяет запросить
`skin(input: {id}) { hash_name name_ids { name name_id } }`, затем
`price_trader_log(input: {name_ids}) { name_id values { price_trader_new time } }`.
Адаптер сверяет полное имя базового скина и точное рыночное имя варианта.
Результат хранится в `csmoney_wiki_price_history` и доступен через
`/api/variants/{variant_id}/market/csmoney/price-history`. API возвращает
только последние 365 дней и только если последняя точка не старше 72 часов;
обновляет успешный кеш раз в 6 часов, ошибку — раз в 15 минут.

Это дневная история цен режима **Trade**, а не подтверждённые сделки и не
история P2P Market. Она отображается отдельно от истории продаж и никогда не
участвует в числе продаж, ликвидности, сравнении площадок или ROI.

## Локальный запуск

Для проверки воркера через VPN используйте отдельный файл
[`docker-compose.csmoney-test.yml`](../docker-compose.csmoney-test.yml).
Он поднимает PostgreSQL, импорт каталога, Gluetun и CS.MONEY-воркер. Образ
воркера собирается из текущего локального кода через `Dockerfile.csmoney`;
тот же образ используется для импорта каталога, поэтому сборка frontend не нужна.

Запускайте команды из корня проекта. Нужен Docker Engine или Docker Desktop
в режиме Linux containers. Если `.env` ещё нет, скопируйте `.env.example` в `.env`.
Используются существующие настройки Surfshark WireGuard:

```dotenv
SURFSHARK_WIREGUARD_PRIVATE_KEY=ваш_ключ
SURFSHARK_WIREGUARD_ADDRESSES=адрес_из_WireGuard_конфига
SURFSHARK_SERVER_COUNTRIES=Poland
```

Первый запуск скачивает браузер Camoufox при сборке образа и импортирует
каталог в тестовую БД. Воркер стартует после успешного импорта и готовности VPN.
Его сетевой режим `service:gluetun` направляет запросы через Gluetun, как
в production. Ключи CSFloat и CSGO Market для этого стенда не обязательны.

```powershell
docker compose -f docker-compose.csmoney-test.yml up --build -d
docker compose -f docker-compose.csmoney-test.yml logs -f --tail=100 gluetun catalog-seed csmoney-worker
```

В логах Gluetun должно быть успешное подключение, у `catalog-seed` —
`Catalogue is ready`, а у воркера — количество добавленных задач и результаты
их обработки. `source=wiki_market_summary result=ok` означает успешную
Wiki-сводку; это не подтверждение получения storefront-лотов. Ответ 403
по-прежнему включает паузу storefront, даже при работающем VPN.

Проверка состояния контейнеров:

```powershell
docker compose -f docker-compose.csmoney-test.yml ps --all
```

Для одного прохода вместо фоновой работы сначала остановите воркер,
оставив готовые БД и VPN, затем запустите его с `--once`:

```powershell
docker compose -f docker-compose.csmoney-test.yml stop csmoney-worker
docker compose -f docker-compose.csmoney-test.yml run --rm --no-deps csmoney-worker python -m backend.app.csmoney_worker --once
```

`--once` обрабатывает одну готовую задачу и завершает процесс; результат
провайдера проверяйте по логам, а не только по коду завершения.

Остановка стенда с сохранением тестовой БД:

```powershell
docker compose -f docker-compose.csmoney-test.yml down
```

Стенд использует отдельный Compose project `true-roi-csmoney-test` и volume
`csmoney_test_postgres`; порты на хост не публикуются. Для удаления именно
тестовой БД добавьте `--volumes` к команде `down`.

Для запуска всего приложения без этого VPN-стенда остаётся
`docker compose up --build`. На production GitHub Actions собирает второй
образ из `Dockerfile.csmoney`; VPS скачивает его из GHCR.

## Python-зависимости

Три requirements-файла разделяют разные окружения:

| Файл | Назначение | Дополнительно к общей базе |
| --- | --- | --- |
| `backend/requirements.txt` | API и общие модули | FastAPI, Pydantic, Uvicorn, python-dotenv, Psycopg |
| `backend/requirements-csmoney.txt` | Браузерный воркер | Camoufox |
| `backend/requirements-dev.txt` | Тесты | pytest |

Файлы воркера и тестов подключают базовый через `-r requirements.txt`;
дублирования общего списка нет. Локальный Docker-стенд устанавливает нужные
зависимости и браузер внутри образа, вручную устанавливать их на хост не нужно.
