# Текущие проблемы production

Состояние проверено 21 сентября 2026 года по production-логам и интерфейсу.
Документ описывает известные ограничения данных. Зелёный health check означает,
что процесс API отвечает, но не подтверждает доступность внешних площадок.

## Сводка

| Приоритет | Область | Текущее состояние | Влияние |
|---|---|---|---|
| P0 | CS.MONEY storefront | Production VPS получает HTTP 403 | Нет снимка десяти реальных лотов |
| P0 | CS.MONEY Wiki fallback | Результат на VPS не виден в INFO-логах; публичный GraphQL также может вернуть Cloudflare 403 | Может отсутствовать даже резервная минимальная цена |
| P1 | CSFloat | Публичная индексная цена доступна отдельно от конкретных лотов; API лотов сейчас сообщает rate limit | В карточке есть цена, а окно лотов пустое |
| P1 | Статусы UI | Успешный ответ нашего API показывается как `live`, даже если конкретный provider недоступен | Пользователь может принять индекс или кэш за живые лоты |
| P1 | Наблюдаемость | Health check проверяет процессы, а не свежесть данных площадок | Успешный деплой не гарантирует рабочие рыночные данные |
| P2 | Логи | Успехи и ошибки Wiki fallback находятся на DEBUG, health check создаёт много access-логов | Причину пустых данных трудно увидеть |
| P2 | Схема БД | Изменения схемы выполняются через `ensure_schema`, Alembic отсутствует | Миграции production-БД сложнее контролировать и откатывать |

## 1. CS.MONEY

### Подтверждённое состояние

После production-деплоя воркер поставил 30 вариантов в очередь, но первый запрос
к странице Market получил HTTP 403:

```text
CS.MONEY scheduled 30 candidate jobs
CS.MONEY storefront returned 403; using Wiki Market summaries for 21600s
```

Это означает следующее:

- `scheduled 30` показывает только размер поставленной очереди и не означает,
  что 30 вариантов были успешно загружены;
- Camoufox-процесс запущен, но storefront блокирует адрес или сессию VPS;
- после первого 403 воркер на шесть часов прекращает запросы к storefront;
- в течение паузы реальные ID лотов, float, seed, наклейки и charms получить
  нельзя;
- обход security challenge намеренно не выполняется.

Следовательно, текущая production-интеграция CS.MONEY находится в деградированном
состоянии: реальные P2P-листинги не поступают.

### Состояние Wiki fallback

Fallback вызывает публичный GraphQL `get_min_available(name)` и при успехе
сохраняет минимальную цену Market и число предложений для точного
`market_hash_name`. Это агрегированная сводка, а не список лотов.

Сейчас нельзя подтвердить, что fallback успешно работает на VPS:

- результат каждого запроса записывается на уровне DEBUG и отсутствует в
  обычных production-логах;
- проверка с внешнего адреса 21 сентября 2026 года получила HTTP 403 HTML от
  Cloudflare на `https://wiki.cs.money/api/graphql`;
- экран `CS.MONEY is temporarily unavailable` означает, что для выбранного
  варианта осталась ошибка и свежая сводка не была выдана.

Даже при исправном fallback список должен показывать `0 listings`: Wiki даёт
только минимум и количество предложений. Интерфейс должен явно различать
«доступна сводная цена» и «доступны конкретные лоты».

### Дополнительные ограничения

- Circuit breaker хранится только в памяти процесса. Перезапуск контейнера
  немедленно сбрасывает шестичасовую паузу и снова обращается к storefront.
- При выборе `Variant: Any` ответ объединяет несколько вариантов. Ошибка одного
  из них может пометить всю секцию CS.MONEY как недоступную.
- `demand probe: observed: 0, unobserved: 5, errors: 0` означает отсутствие
  наблюдаемых продаж в проверенной выборке. Это не доказывает нулевой спрос и
  не относится к успешности получения лотов CS.MONEY.
- Истории подтверждённых продаж и заявок быстрой продажи CS.MONEY по-прежнему
  нет. Wiki Trade history является отдельным рядом котировок и не должна
  использоваться как история продаж.

### Возможные исправления

1. Добавить INFO-событие или диагностический статус для каждого результата Wiki:
   `success`, `cloudflare_403`, `variant_not_found`, `invalid_payload`, `timeout`.
2. Проверить GraphQL непосредственно из контейнера на VPS и сохранить HTTP
   status, content type и время ответа без записи тела challenge-страницы.
3. Хранить circuit breaker в PostgreSQL, чтобы рестарты не сбрасывали блокировку.
4. Показывать отдельные состояния `listings unavailable`, `summary available`
   и `provider unavailable`.
5. Не объединять ошибку одного Normal/StatTrak/Souvenir-варианта в общий статус
   всех выбранных вариантов.
6. Для настоящих десяти лотов найти стабильный разрешённый источник storefront
   или официальный API. Wiki fallback не может восстановить эти данные.

## 2. CSFloat

### Почему цена видна без списка лотов

В проекте используются два независимых потока CSFloat:

1. Публичный `/api/v1/listings/price-list` возвращает минимальную индексную цену
   и количество по `market_hash_name`. Эта цена сохраняется в
   `marketplace_listings` и показывается в карточке wear.
2. `/api/v1/listings` возвращает конкретные лоты и используется в модальном
   окне. Этот запрос зависит от доступности API и его rate limit.

Поэтому `$58.17` в превью и `0 listings` в окне не противоречат друг другу:
первая цифра является публичной индексной котировкой, а конкретные лоты получить
не удалось.

Production-лог содержит:

```text
CSFloat provider_unavailable: CSFloat временно ограничил частоту запросов
```

Это классифицировано как rate limit или временная недоступность, а не как
подтверждённый неверный ключ. Неверный или отсутствующий ключ должен давать
`provider_auth_failed`. Пока ограничение частоты мешает проверочному запросу,
фактическое состояние ключа остаётся неопределённым.

### Риски текущего поведения

- Карточка не объясняет, что показана индексная цена без ID конкретного лота.
- Общий статус интерфейса может говорить `live`, потому что наш endpoint вернул
  HTTP 200 с данными и описанием ошибки provider.
- Проверка ключа использует маршрут семейства listings и сама расходует его
  лимит. Затем пользовательский запрос конкретных лотов обращается к тому же
  семейству маршрутов.
- Цена из индекса пригодна как рыночный ориентир, но не гарантирует, что
  конкретный лот можно открыть и купить в момент просмотра.

### Возможные исправления

1. Подписать цену как `CSFloat index` или `market minimum`, если `listing_id`
   отсутствует.
2. Показывать раздельно `price index available`, `listings rate-limited` и
   `authentication failed`.
3. Не использовать индексную цену как визуальное доказательство доступности
   конкретных лотов.
4. Пересмотреть частоту auth probe и общий limiter для всех запросов семейства
   `/api/v1/listings`.
5. После окончания cooldown выполнить один read-only запрос с production VPS:
   HTTP 401/403 подтвердит проблему ключа, успешный ответ подтвердит только
   временный rate limit.

## 3. Кэш и частично загруженные данные

Кэш является общим для разных типов данных, но их смысл различается:

- `marketplace_listings` содержит минимальные котировки и количество;
- `marketplace_active_listings` содержит конкретные лоты CS.MONEY;
- `marketplace_variant_details` содержит подробности варианта других площадок;
- `marketplace_syncs` хранит время массовой синхронизации индекса.

Наличие цены в первой таблице не означает наличие записей во второй или третьей.
Это остаётся основной причиной визуально «частичной загрузки».

Для CSFloat и CSGO Market подробный кэш теперь хранит отдельные timestamps и
ошибки для `listings`, `sales` и `buy_orders`. Неудачное частичное обновление не
переносит старые данные на новый общий timestamp: упавшая часть остаётся
`stale`/`unavailable` и повторно запрашивается внутри общего TTL. API возвращает
машиночитаемый `components`, а UI показывает состояние открытой вкладки.

Остаётся унифицировать эту модель с индексными котировками, CS.MONEY summary и
provider diagnostics: источник (`index`, `summary`, `listing`), авторизация,
rate limit и число реально полученных лотов пока не сведены в один общий статус.

## 4. Логи и мониторинг

Текущая проверка деплоя подтверждает:

- API container перешёл в `healthy`;
- crawler и demand worker имеют состояние `running`;
- PostgreSQL принимает подключения.

Она не подтверждает получение хотя бы одной свежей цены или одного лота от
каждой площадки. Частые запросы Docker health check также создают большое число
строк `GET /api/health 200 OK` и скрывают полезные события.

Рекомендуемые изменения:

1. Добавить provider diagnostics с последним успешным запросом, последней
   ошибкой, возрастом данных и состоянием circuit breaker.
2. Добавить readiness-политику отдельно от process health. Отказ одного внешнего
   provider не должен останавливать API, но должен быть виден как degraded.
3. Исключить `/api/health` из обычного access-log или вынести его в отдельный
   уровень.
4. Логировать переход состояния один раз: `healthy -> rate_limited`,
   `healthy -> blocked`, `blocked -> recovered`, без повторов по каждому скину.

## Уже исправлено и не относится к текущим дефектам

- поиск учитывает полное имя варианта, включая wear и StatTrak;
- просроченные котировки не участвуют в ROI;
- WhiteMarket прекращает массовый fanout при ошибке токена;
- частичный сбой detail-кэша CSFloat/CSGO Market больше не делает старые
  listings/sales/buy orders свежими;
- production Compose использует стабильные имена контейнеров и ротацию логов;
- deploy защищён `flock` и проверяет запуск API и обоих воркеров.

Эти изменения уменьшают последствия ошибок, но не восстанавливают внешний
доступ к данным CS.MONEY и CSFloat.
