# Аудит CS.MONEY — 30 сентября 2026

## Вывод

Архитектура интеграции в целом соответствует проекту: локальный каталог,
отдельный storefront-adapter, фоновый сбор, PostgreSQL-кэш и явное разделение
Market/Trade. Переписывать всё или добавлять новый broker сейчас не нужно.

Главное внешнее ограничение — **403 на production storefront**, зафиксированный
в документации 21 сентября. Wiki не восстанавливает реальные десять лотов:
он даёт только отдельную сводную цену, а его доступность с VPS не подтверждена.
Production повторно не проверялся в этом аудите.

Помимо известных ограничений найдены **5 проблем P1 и 6 проблем P2** в backend,
контрактах и UI. Приоритет — изолировать сбои, разделить retry двух источников,
обеспечить точную атрибуцию варианта и честно показывать происхождение цены.
Application code в рамках аудита **не изменялся**.

## Что уже сделано правильно

* Поиск не обращается во внешний API на каждый пользовательский запрос.
* Браузер вынесен в отдельный воркер; API отдаёт кэш и ставит refresh в очередь.
* Очередь дедуплицируется по варианту; claim использует `FOR UPDATE SKIP LOCKED`.
* Проверяются сортировка цен, точное имя, уникальность ID и предел десяти лотов.
* Деньги адаптера нормализуются через `Decimal` в целые USD-центы.
* Частичная первая страница не выдаётся за подтверждённое отсутствие предложения.
* Запись Wiki summary удаляет прежние конкретные лоты, не создавая фиктивных ID.
* Stale-котировки исключаются из ценового сравнения и ROI.
* Trade history подписана как котировки, а не продажи; она не влияет на ROI,
  ликвидность и счётчик продаж.
* GraphQL использует variables, проверку точного имени, Content-Type, размера
  ответа и поля `errors`.
* История продаж/quick sell и неподдерживаемые attachment-фильтры CS.MONEY
  отключены в capabilities.

## P1 — исправлять первыми

### 1. Ошибка HTTP-чтения Wiki может завершить весь воркер

**Код:** `backend/app/csmoney_worker.py:109–115,129–134,174,194–198`;
чтение ответа — `backend/app/csmoney_wiki.py:44`.

При оборванном chunked-ответе возможен `http.client.IncompleteRead`, который не
входит в перечисленные исключения fallback. В Wiki-only режиме он выходит из
`process_one(None)` и завершает `run`; при первом storefront 403 также может
помешать установке breaker. Рестарт контейнера восстанавливает процесс, но
сбрасывает in-memory паузу, leased-задача остаётся незавершённой.

**Минимальное улучшение:** нормализовать транспортные ошибки на границе Wiki;
добавить защиту уровня обработки job, безопасное defer и классифицированный лог.
Не скрывать неожиданные ошибки без диагностики. Тест: оборванный ответ при
первом 403 и во время уже действующей паузы.

### 2. Кратковременная ошибка Wiki блокирует refresh на шесть часов

**Код:** `backend/app/csmoney_worker.py:114,133`;
`backend/app/csmoney_data.py:40–42,53–56,71`.

Fallback откладывает задачу на 21 600 секунд. Через 15 минут API снова разрешает
enqueue, но upsert меняет только priority, не время готовности. Пользователь
получает `refresh_queued=true`, хотя задача ещё несколько часов не исполняется.
Пауза storefront применяется к независимому Wiki-источнику.

**Минимальное улучшение:** отдельные backoff/cooldown для storefront и Wiki;
развести `next_attempt_at` и активный lease. Не просто обнулять lease при enqueue:
это может позволить забрать ещё выполняющуюся задачу. Тест: Wiki восстановился
через 20 минут, пользовательский запрос действительно доступен к обработке.

### 3. Отсутствующая фаза принимается за запрошенную

**Код:** `backend/app/marketplaces/csmoney.py:168–169`;
`backend/app/csmoney_data.py:183–184`.

Если полное имя совпало, `actual_phase is None` считается достаточным даже при
запросе Ruby/другой конкретной фазы. Лот с общим именем Doppler и отсутствующей
фазой может дать цену не тому варианту. Один ID затем может перемещаться между
вариантами при upsert.

**Минимальное улучшение:** для фазового варианта требовать подтверждённую фазу
или иной документированный идентификатор; неизвестное значение не считать
совпадением. Тесты: missing/mismatched phase и один ID для разных фаз.

### 4. Происхождение Wiki-цены не объясняется в карточке ROI

**Код:** `backend/app/market_comparison.py:300–309`;
`frontend-react/src/features/catalog/CatalogPage.tsx:129–132`.

Свежая summary участвует в сравнении согласно документации, но opportunity
помечает источник только как `lowest_ask`. Карточка показывает прибыль/ROI без
объяснения, что это агрегированный ориентир без конкретного доступного лота.
Предупреждение присутствует лишь в модальном сравнении
(`frontend-react/src/features/catalog/ListingDialog.tsx:359`).

**Минимальное улучшение:** передавать provenance обеих сторон сделки и показывать
`summary/index/listing` рядом с результатом. Не менять формулу прибыли: это
проблема контракта и представления достоверности, а не арифметики.

### 5. Исключение CS.MONEY обрушает сравнение остальных площадок

**Код:** `backend/app/market_comparison.py:58–66`.

Все futures читаются без изоляции исключений. Если `get_csmoney_prices` выбрасывает
ошибку, три исправных ответа не возвращаются. Обычный JSON с полем `error`
такого эффекта не вызывает; проблема именно в exception-path.

**Минимальное улучшение:** обрабатывать каждый future отдельно, сохранять успешные
результаты и возвращать диагностический статус упавшего источника. Общий сбой
БД не следует маскировать как изолированный отказ provider. Тест: один adapter
выбросил исключение, остальные цены и opportunities сохранились.

## Условные риски, не подтверждённые production-инциденты

* **Lease без ownership/fencing:** `backend/app/csmoney_data.py:64–104`.
  Если задача выполняется дольше 300 секунд или работают два collector-а, старый
  исполнитель может записать результат и удалить задачу нового владельца.
  Нужен token/generation и условное завершение; актуальность возрастает при
  масштабировании. Не требуется новый broker ради этого исправления.
* **Будущий timestamp считается fresh:** `backend/app/csmoney_data.py:35–37`.
  Проявление требует рассинхронизации часов/неверной записи. Стоит ограничить
  допустимое отклонение и проверить TTL-тестом.
* **Cache stampede Wiki history:** `backend/app/csmoney_wiki.py:161–175`.
  Одновременные cache misses не дедуплицируются; нужен coalescing/ограничение
  запросов при реальном подтверждённом всплеске нагрузки.

## Известные ограничения, которые аудит не объявляет новыми

Подробности — `docs/KNOWN_ISSUES.md`:

* Storefront/Wiki могут возвращать Cloudflare 403; обход challenge не выполняется.
* Circuit breaker в памяти сбрасывается при рестарте.
* Успех/ошибка Wiki плохо видны в INFO-логах.
* Ошибка одного варианта при `Any` может стать общей ошибкой площадки.
* HTTP 200 нашего API и статус контейнера не означают live-данные provider.
* У Wiki summary нет конкретных ID, float, attachments и реальных десяти лотов.
* CS.MONEY sales history и quick sell не реализованы; Trade quotes их не заменяют.

## Рекомендуемый порядок работы

1. **Один backend-срез:** нормализованные ошибки Wiki, живучесть job-loop и
   отдельный короткий retry fallback. Добавить INFO-события результата без
   секретов/тела challenge. Это наименьший полезный следующий шаг.
2. **Корректность атрибуции:** фазы, положительные bounded cents, соответствующие
   негативные fixtures.
3. **Контракт + UI:** provenance обеих цен, компонентная свежесть, detail errors,
   возможность аналитики варианта без лота и срок свежести Trade history.
4. **Устойчивость состояния:** persisted circuit breaker и разделение lease/retry;
   fencing до добавления второго collector-а. Проверить реальные SQL-переходы
   на отдельной тестовой PostgreSQL-БД, не только fake connections.
5. **Отдельная операционная проверка:** после разрешения владельца проверить
   источник из VPS-контейнера, записать status/content-type/duration и найти
   стабильный разрешённый источник/официальный API для реальных лотов.

Первые четыре пункта улучшат честность и живучесть приложения, но **не устранят
внешний 403**. Новые площадки/Redis/крупный рефакторинг сейчас не приоритет.
Ключевой учебный концепт: состояние процесса, свежесть компонента и доступность
источника — разные оси; retry источника не должен подменять lease задания.
